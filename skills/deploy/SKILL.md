# 部署

## 动手前
1. `stack_probe` 确认构建命令、CI 系统、容器配置与迁移执行方式。
2. 读现有 Dockerfile、CI workflow、`.env.example`，提取基础镜像、构建阶段划分、变量命名规范。
3. 确认部署目标的既有约束（镜像仓库、资源限制、健康检查路径、发布窗口）。

## 实现准则
- **构建可复现**：锁定依赖版本（lockfile 必进仓库），不使用 `latest` 基础镜像标签。
- **镜像精简**：多阶段构建，运行阶段只留运行时依赖与产物；不以 root 运行。
- **配置外置**：密钥与地址全部走环境变量，代码里不留默认凭据；新增变量同步到 `.env.example` 与部署清单。
- **健康检查**：沿用既有 healthcheck 路径与超时；新服务必须能被探测到就绪。
- **发布可回滚**：发布前明确回滚方式（镜像 tag 回退、迁移 down、开关关闭），并验证一次。
- **迁移与发布解耦**：迁移先于新版本上线，且旧版本在新 schema 下仍可运行（兼容窗口）。

## 完成前必查
- [ ] 本地 `build` 通过，产物可直接运行
- [ ] 镜像构建成功且体积无明显膨胀
- [ ] CI 配置语法有效（本地 lint 或用 CI 的校验命令）
- [ ] 新增环境变量已在 `.env.example` 与部署配置中声明
- [ ] 健康检查与回滚步骤写进回答

## 反模式
- 把密钥写进 Dockerfile 或 workflow
- 跳过测试直接发布
- 迁移与代码在同一窗口强耦合、无兼容期

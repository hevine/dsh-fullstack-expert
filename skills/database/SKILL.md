# 数据库

## 动手前
1. `stack_probe` 确认数据库类型、ORM/迁移工具（Prisma、Drizzle、TypeORM、Alembic、Knex、原生 SQL）。
2. 读最近 2-3 个迁移文件，提取命名规范、时间戳格式、up/down 写法。
3. 确认目标环境的迁移执行方式（启动时自动迁移、CI 执行、人工执行）。

## 实现准则
- **向后兼容优先**：先加字段（可空或带默认），再迁数据，最后删旧字段；一次迁移不混做三种事。
- **可回滚**：每个迁移必须有 down 或明确的回滚脚本；不可逆操作在注释里写清。
- **锁与耗时**：大表加索引/加非空默认值评估锁表时长，必要时分批（backfill）执行。
- **数据回填**：脚本幂等，可重复执行；先小批量验证再全量。
- **索引依据**：新增索引要能说清对应查询与选择性，不为"以防万一"加索引。
- **事务**：跨表一致性写入放同一事务；长事务拆开，避免持锁过久。

## 完成前必查
- [ ] 迁移在空库上能跑通，在含数据副本上能跑通
- [ ] down 可执行（本地验证一次）
- [ ] ORM 模型与迁移后的实际 schema 一致（`prisma validate` / `alembic check` 等）
- [ ] 相关仓储层测试通过
- [ ] 列出受影响的查询与调用方

## 反模式
- 一个迁移里既改结构又做全量数据回填
- 直接 `DROP COLUMN` 而不留兼容窗口
- 用 ORM 同步特性在生产上自动改表
